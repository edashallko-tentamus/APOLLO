## What this is

Validation is GAMP 5 Category 5 (bespoke), documented per module (URS, FS, RTM, risk assessment, IQ/OQ/PQ).

## How to run it (do this for Alex)

1. `npm install` (installs the embedded PostgreSQL, PGlite; no admin rights or database server needed)
2. `npm test` (builds a fresh in-memory database and runs every rule test; all must pass)
3. `npm start`, then open http://localhost:3000 in the Browser pane
4. `npm run reset` deletes the local database (`data/pgdata`) so the next start rebuilds it with demo data. Use it after changing migrations or the seed.

Alternative engine: set `DATABASE_URL=postgres://user:pass@host:port/db` to use a real PostgreSQL server instead of PGlite. Both engines are supported by `server/db.js`.

**First run on a new machine:** this slice was built and tested against PostgreSQL 16 through the wire-protocol client. The PGlite path (`server/db.js`, the `pglite` engine) was written but could not be exercised where it was built. If `npm test` or `npm start` fails on PGlite, fix the adapter in `server/db.js` (result normalization, numeric types, dates) rather than changing the SQL. Then run `npm test` and `npm run test:browser` (needs Playwright: `npx playwright install chromium` if missing) until both pass.

## Architecture (keep it this simple)

- `db/migrations/*.sql`: the schema. **Business rules live in the database** (constraints, triggers, functions) so no screen, script or integration can bypass them. Migrations run once, in order, tracked in `public.schema_migrations`. Never edit a migration that may have been applied to a database you need to keep; add a new numbered migration instead. (In the Sandbox, editing then `npm run reset` is acceptable.)
- `db/seed.sql`, `db/seed_*.sql`: fictional demo data, each file applied once (tracked like migrations). Add new demo data as a new `seed_NNN_*.sql` file so existing Sandbox databases pick it up.
- `db/tests/*.sql`: rule tests. Each uses `pg_temp.expect_true` / `pg_temp.expect_error` and ends with `SELECT ... AS result FROM results`. Every new rule gets a test.
- `server/`: plain Node (no frameworks). `server.js` (HTTP + static files), `routes.js` (JSON API; thin, no business logic), `db.js` (engines, transactions, migrations), `pgwire.js` (minimal PostgreSQL client).
- `public/`: plain HTML/CSS/JS modules, no build step. `js/grid.js` is the spreadsheet grid (link columns take `href(row)`; `options(row)` can differ per row; `detail` shows a panel under a row, used for each sample's tests); `js/combo.js` is the smart dropdown, applied automatically to every `<select>` and used by grid pick-list cells; `js/pages/*.js` are screens (`admin.js` holds the Admin pages).
- Labs: the browser sends the current lab as `x-site-id`; `routes.js` scopes lab lists (orders, intake, outbox, dashboard counts) to it with `currentSite()` and checks record access with `checkSite()`. The database independently refuses writes to labs the user is not assigned to.
- Page headers take an audit scope: `pageHeader(title, subtitle, actions, { kind, id })` adds the audit-trail icon; scopes are defined in `AUDIT_SCOPES` / `AUDIT_LISTS` in `routes.js`, and `audit_record_ref()` (migration 004) gives every audit entry a label and a link. Give every new page an audit scope and make every ID a link (`link()` in `app.js`, or a grid `link` column with `href`).

Enum arrays (Chemical Type, storage conditions) are sent to the database as Postgres array text and parsed back in that file. ## Non-negotiable GxP patterns (already built; follow them for every new table)

- Every regulated table has `id uuid`, `record_version`, `created_at/by`, `modified_at/by`, and is wired with `CALL make_gxp('table')`. This gives: a database-written, append-only `audit_log` (old and new values per field, who, when, reason), automatic versioning, and **no hard deletes** (records are set Inactive or Retired).
- Every write runs inside `db.tx({ userId, reason }, ...)`, which sets `lims.user_id` and `lims.reason`. Edits to regulated records require a Reason for Change (the screens ask for it). Commercial draft tables (projects, quote versions and lines) use `make_gxp('table', false)`: still audited, reason optional.
- A migration that changes existing regulated rows (not just new tables) runs into the same rules as a person: lab access, permissions and signatures. The `system` user has none of these by design. Do the change as a real user who may make it (e.g. the record's creator) with `script_signature('...')`, then restore `system` (see the conversion loop in 011). Fresh test databases often hold no such rows, so also test every new migration on a copy of Alex's data before converting it (found 2026-10-13 with 011).
- Before any real GxP data: separate database roles for the app and administrators so nobody can disable the audit triggers. Built in 0.33.0 (migration 056, `db/roles_setup.sql`, `LIMS_MIGRATE_URL`); the Sandbox still runs as one account.

## Decisions already made (details in the vault decision notes, dated 2026-10-12)

- **Clients:** status Active / On Hold / Inactive. On Hold allows ordering and testing but blocks report release; Inactive blocks new orders but still releases reports for work in the lab. Parent Client exists, but nothing cascades (status, holds, contacts, visibility). Regulated (GMP) client flag.
- **Contacts:** one record per person (email unique system-wide), linked to many clients through `client_contact`, with roles per client: Primary (one per client), Secondary (many), Ordering, Receives Report, Billing, Quality.
- **Analytes:** static master table independent of Inventory (Chemical, Microbiological, Physical/General; CAS validated, chemicals only).
- **Test catalogue (Workflow Designer step 1):** pricing modes Base Price Only, Base + Preparation Fee, Analyte Selection (list = base + prep + selected analyte prices). Standard TAT (maximum; business or calendar days), per-test cutoff time, rush fee schedule, public catalogue flag. Pricing is stored outside the validated Test Version.
- **Rush fees:** reusable named schedules with tiers (TAT, % or flat surcharge, "requires intake approval" default with per-test override, escalation hours). Quotes copy surcharges and carry a discount % per tier.
- **Projects:** reusable client-specific quoted test packages, versioned (Draft, Submitted for Quote, Quoted, Accepted, then Superseded/Rejected/Expired). Lines lock when quoted. List price is a snapshot (never typed). Removing analytes recalculates list price and keeps the negotiated discount %. Accepting list pricing is itself a project (no discounts). Parent projects can be shared with child sites when flagged.
- **Quoted-only ordering:** every ordered test must trace to an accepted, unexpired quote line (`orderable_lines(client)`). Exceptions with their own source: Client OOS Retest and non-billable Lab Investigation Retest. **Superseded in 0.36.0** (Alex, 2026-10-21): any test of the ordering lab can be ordered at its list price; an accepted quote line still wins.
- **TAT clock:** logging day is Day 0; after the test's cutoff Day 0 moves to the next working day (test still enters the pool); business-day tests received on weekends or holidays start the next business day; due date per requested test, sample = latest test, order = latest sample. Sites need a time zone and holiday calendar.
- **Rush handling:** auto-accepted tiers flag the intake dashboard; approval-required tiers notify intake, run at standard TAT and price until approved, escalate if ignored; "Rush not accepted" sends a fixed automatic email naming the staff member.
- **OOS:** Full Phase I (21 CFR 211) for GMP clients, Check and Acknowledge otherwise (site default); automatic data checks for both; the OOS result is held, other results may be released on a partial CoA (client setting); email to client on release, not detection; client retests are always re-preps; billing by QA determination (Confirmed or Inconclusive billable, Lab Error not billable incl. rush); retest CoA is new and includes all tests on the order.
- **Stability:** separate quoting module; study quoted whole (conditions x timepoints matrix); T0 baseline at placement; pulls from T1 create Lab Orders on the pull date; tolerance per timepoint; billed per pull; per-timepoint and cumulative reports; material sufficiency check; chambers are Equipment; annual price escalation option.

## Slice 3 decisions: Inventory (2026-10-12; built in migration 005, designed with Alex in Claude chat)

- **Build order:** Inventory now, before the Test Workflow Designer, because workflow steps will consume inventory lots.
- **One Inventory Lot object** for every material, with a Chemical Type multi-select (Consumable, In-house mixture, Solvent, Reagent, Media, Reference Standard, Microbiological Strain). Chemical comes from the controlled **Chemical list** (name, CAS unique and check-digit validated, optional link to an Analyte); consumables and mixtures can be described instead. Each lot gets a lab ID `INV-000001` (the Resource ID for mixtures).
- **Lists:** Chemicals, Suppliers/Manufacturers (shared by all labs) and Storage locations (per lab, nested, with the conditions each provides, and a "holds samples" flag) are maintained by **Lab Supervisors, QA, General Managers and administrators**. Warning rules (thresholds) likewise.
- **Job role (interim):** `app_user.job_role` (Analyst, Intake, Lab Supervisor, QA, General Manager, Account Manager), set by administrators on Admin > Job roles, audited with a reason. Replaced later by Roles and Permissions.
- **Inventory belongs to a lab**; the lab access rule applies. **Transfer** to another lab writes the quantity off at the sender and creates a new lot at the receiver (same manufacturer lot, expiry and Supplier COA, linked back) **In Transit**; the receiving lab **receives** it like a new lot.
- **Purchase flow on the lot itself:** Requested -> Approved (**Lab Supervisor** or admin) -> Ordered -> Received. Reorder is available on any lot. Receive completes the same lot (never a second one). Not usable until received.
- **Stock movements** (Receipt, Usage, Adjustment, Transfer Out, Disposal) are append-only; quantity on hand is their sum and **may go negative** (flagged "reconcile"). Adjustments and Dispose need a reason. Quantity received and unit are locked after receipt (correct with an Adjustment).
- **Use eligibility:** a lot can only be used when received, Available, in date and not past retest. Storage condition must be one the location provides (refused otherwise).
- **In-house mixtures:** made from component lots in one step (each component gets a Usage); expiry defaults to, and can never be later than, the earliest-expiring component.
- **Supplier COA:** never required to receive. The file is stored unchanged with its SHA-256 fingerprint (`document_file`, no edits or deletes). **AI reading (status: Proposed, Alex approved the idea):** if `ANTHROPIC_API_KEY` is set, the uploaded COA is sent to Anthropic's API (`LIMS_AI_MODEL`, default `claude-sonnet-5-5`), which proposes values with the text it read them from; a person reviews them beside the document and confirms (with a reason) before anything is written to the lot. The proposal is kept unchanged on the COA record. Off by default: needs IT approval and a key. Without a key the same screen is manual entry beside the document.
- **Sample storage:** samples get a storage location (must hold samples and provide the sample's condition) and a retained quantity (cannot exceed what was received); low retains warn, never block (Inventory > Sample storage, fill down to shelve many at once).
- **Warning rules** (Threshold Rule types): Lot Quantity (Percentage of Base or Absolute Max-Min), Lot Expiry (Days Until/Since), Sample Retain (Percentage of Base or Absolute). Seeded: low stock below 20% of received, expiring within 30 days, retain below 25%.

- **What it is:** on a draft version's Review tab, "Write the verification protocol" (signed "Prepared by", methods.design). `server/verification.js` writes it from the design: URS (what the lab needs: analytes and reporting, specification, QC, data integrity, review, timepoints, split-offs, hold points, order status) and FRS (one per step, per QC criterion, the comparison with the specification, order statuses), the samples (S1 typical, S2 below the LOQ, S3 outside the specification, S4 below the LOD when the test reports ND), every value the run will enter, and the **expected results from an independent calculation** (its own formula parser with ordinary maths precedence, exact rationals over BigInt, rounding, LOQ/LOD reporting, dilution factors, conformance). Unrounded results must agree to 9 significant figures; reported text and conformance exactly. Inputs are steered (log-scale search then bisection on the final formula's latest reading) to hit each case, and nudged off rounding and LOQ boundaries.
- **Design fingerprint:** `test_version_definition()` / `test_version_config_hash()` (steps, configs, equipment types, dependencies, analytes, rounding; no ids or history). A change after the protocol voids it (refused at execution and at the gate).
