# Decision - Workflow Step Types Cascade Under One Definition Object

[[Workflow Step Definition]] is one object for all step types, with a Step Type field determining which type-specific configuration fields cascade underneath — both in the data model and in the step builder UI. Separate objects per step type were considered and rejected. The generic mechanics ([[Step Dependency]], [[Step Authorization]], [[Acceptance Rule]], [[Decision Rule]]) apply to every type; what differs per type is the configuration below.

## The eleven step types and their cascading fields

- **Batching** — defines the [[Batching Rule]] for this Test: Max Samples Per Batch (client samples only — QC rides on top), and Required QC Types, each configured with a QC Class (Prep QC travels through sample prep like a real sample; Analytical QC is instrument-sequence only), a Frequency (once-per-batch count, or every-N-samples interval producing opening + closing bracketing entries), and ACCEPTANCE CRITERIA: one or more per QC sample, each a Limit Type plus adaptive fields — range types take min/max (Recovery %, RSD, Stdev, Area Counts, Tailing Factor, Retention time, Signal-to-noise, Resolution), max-only types take max (RPD, Blank threshold — a value or a limit reference like ½ LOQ), qualitative types take no numbers (Absence, Presence, Identified). Criteria are DECLARED here but EVALUATED automatically wherever their inputs first exist — recovery at Calculation, tailing factor at Data Entry, absence at the count reading — with failures flowing through [[Acceptance Rule]] (pass/fail/repeat/review). Each criterion carries a DEFAULT plus per-analyte overrides — exceptions only, selected from the Test's configured analytes — for methods like pesticide residue panels where analytes recover differently (e.g. captan 60–130, chlorothalonil 50–140, everything unlisted at the 80–120 default); the same default-plus-override shape as Calculation's per-analyte formulas. FLAGGED, deferred: a full-analyte-list editing view (every analyte shown with its effective limit, defaults inherited/greyed, editable inline) was raised as possibly needed for editing recoveries at scale — deferred in favor of exceptions-only for build simplicity, but the exceptions-only storage doesn't preclude adding that view over the same data later. Evaluation is per analyte: one Matrix Spike yields a verdict per analyte against its own limit, so a 200-analyte spike can pass 198 and flag only the genuine exceptions for review, never the whole spike. Spiking and material assignment are deliberately NOT part of the definition — they happen per batch at execution via right-click (see [[Test Batch]]), for flexibility. A Matrix Spike gets its spike at the batch, its own weight at the Weighing step, travels through digestion and dilution, and its recovery is calculated at the Calculation step and judged against the criteria declared here.
- **Weighing** — the batch is weighed out against a balance ([[Equipment]] Type, not a specific unit — resolved at execution, where Equipment Tag and calibration currency already gate availability). A connected balance auto-fills the reading; otherwise the analyst enters it manually — behavior, not a configured mode, so there is no entry-mode toggle. A Default Weight (with tolerance) can be populated as the per-entry target. Weighs client samples and Prep QC only; Analytical QC skips prep. At execution, the equipment actually used is MANDATORY tracking per entry — the tech multi-selects rows and right-clicks to add equipment to the selection (same context-menu pattern as batch spiking); the step cannot complete while any entry is missing its weight or its equipment. A tagged-out or calibration-lapsed balance is blocked in the equipment picker.
- **Preparation** — deliberately ambiguous and flexible: creator-named (digestion, titration, ignition, anything). Definition-time config is minimal: step name, an optional procedure reference shown to the tech at execution, and a free-form field builder (label + type: Number/Text/Time/Date). Those custom fields are step-level — filled once per batch run (e.g. digestion temp, time on/off); per-sample free-form is the Note column at execution, exception-based: following procedure needs no notes, only deviations get written. Equipment and inventory tagging (including spiking) are an opportunity at execution via the same right-click menu — available, not mandatory, unlike Weighing where equipment is required. The happy path is a single Part 11 sign-off completing the step for the whole batch, certifying all entries were prepared per procedure — one signature, not one per sample. Items tagged flow through [[Material Usage Record]] as everywhere else.
- **Plating/Inoculation** — microbiology: sample transferred onto or into growth media. Definition-time config: creator-named step, optional procedure reference, Expected Media as guidance only (chemical identity shown to the tech — the actual media lot is tagged at the batch via right-click, per the batch-time flexibility principle), and Plates Per Entry (duplicate plating — each entry produces N plates, creating a sub-entry structure the downstream Incubation and colony-count Data Entry steps inherit). Media (a Chemical Type already in [[Inventory Lot]]) flows through [[Material Usage Record]]. When fed by a Serial-mode Dilution, the analyst SELECTS which levels to plate per entry — typically the bracketing levels expected to land in the countable range, per SOP guidance and analyst judgment (USP 61 practice). Unplated levels are recorded as "not plated" with NO justification required — level selection is normal practice, not a deviation. Plate math = selected levels × plates per entry; the mandatory media-lot gate applies to plated levels only. Prep QC entries (Positive/Negative Control) are plated like real samples, per their QC Class from the Batching step. Added because Incubation only covered time, not the act of introducing sample to media.
- **Incubation** — definition-time config: incubator as [[Equipment]] Type (specific unit resolved at execution, tag-out/calibration gating inherited), Target Temperature ±, and Target Duration with an acceptance window (finishing outside it flags for review via [[Acceptance Rule]]). At execution, Time In and Time Out are captured PER LOAD, not per batch: labs often split one batch's plates across multiple incubators, so the tech multi-selects plates and assigns them to incubator loads (right-click, same pattern as everything else) — each load gets its own incubator, its own time in/out pair, and its own duration-window check. The step completes only when every plate is assigned, out, and either in-window or flagged.
- **Dilution** — analysts enter what was added, never factors: each dilution field records Aliquot (mL) + Diluent Added (mL), with the diluent itself attached per dilution via right-click ("how much was added of what") through [[Material Usage Record]]. The system derives final volume (sum) and dilution factor (final ÷ aliquot), compounding across fields — e.g. 10+40 then 5+45 = 5× · 10× = 50× — and every entry's derived chain flows to the Calculation step with the sample weight from Weighing. Each entry has multiple optional dilution fields (a wizard setting, default 3) — deliberately more than the procedure needs, so out-of-procedure re-dilutions (e.g. getting within the calibration curve) have a place to land; blank fields mean unused. Wizard config: Mode (Single or Serial), default aliquot + diluent amounts pre-filling Dilution 1, Dilution Fields Per Entry, Expected Diluent as guidance only. Serial mode (micro, USP 61/62) follows the same added-amounts rule, not declared ratios: definition sets default amounts (e.g. Initial 10 g + 90 mL, Transfers 1 + 9 mL, standard depth 3) and each level's factor is derived; optional headroom transfers let a tech extend the series at the bench (e.g. to 10⁻⁴ for an expected high count). Every filled level is retained and tracked. OPEN, per-lab: the Initial dilution as built mixes units (grams of sample + mL of diluent, standard w/v) — whether every Tentamus micro lab works this way is unconfirmed and may vary by lab; left as designed pending lab input. Which levels actually get plated is decided downstream at the Plating step, not here.
- **Split off Test** — spawns an existing [[Test]] from the catalog as a new [[Requested Test]], automatically available for batching. Narrowed to the reflex role: for tests that could not be ordered because their necessity is discovered mid-testing (e.g. a USP 62 screen shows growth → identification is spawned). Triggered by a [[Decision Rule]] firing on a finding, or manually by the analyst for cases no rule anticipated. NOT for package siblings ordered up front — that's the package pattern, below. The only step type that creates a new execution instance of another object from inside a workflow.
- **Hold Point** — stops the workflow until a NAMED external dependency completes: the specific [[Requested Test]] it was configured to wait on at definition time, either one spawned by a Split off Test or an ordered sibling (e.g. the withanolides Calculation waiting on the package's Loss on Drying). Never a general barrier — unrelated tests on the same sample do not block, and a test's result completes and is approvable as soon as its own named dependency is done. Whole-sample completeness for the final CoA is a separate downstream gate, the existing [[Report Release Blocking Rule]], not Hold Point's job. Explicitly NOT a QA approval gate: QA sign-off is different than Hold Point and lives in QC Review.
- **Calculation** — a test final result calculated via [[Calculation Formula]], token-based: every token is pulled from live workflow data, never typed — the instrument reading from Data Entry, the derived dilution chain, the sample weight from Weighing, step free-form fields, constants, and sibling test results. A sibling-result token (e.g. Loss on Drying for dry-basis potency) is only available if a Hold Point in this workflow names that test — dependency and formula validity police each other; the formula physically cannot reference a result that isn't guaranteed to exist. One formula template applies per analyte across the panel (each analyte with its own reading and Reporting Unit; per-analyte override for exceptions), so a 100-analyte panel gets one formula, not a hundred. Output lands in each analyte's Reporting Unit via the Unit of Measure equivalency table, and every result keeps its full navigable lineage. Spike recovery is computed here when the batch's Spike usage records exist, but its acceptance criteria are DECLARED at the Batching step with the QC sample, not here. As a Calculation Formula record, the formula itself falls under [[GMP Record Change Control Rule]] — editing it is a permission + signature + reason event.
- **Data Entry** — analyst uploads raw data or enters it manually. Wizard config: Captured Value label + unit, and Require Raw Data Attachment (default on — the instrument export or printout attaches to the batch as the ALCOA source record, and the step cannot complete without it; uncheck per-step for genuinely manual observations with no instrument output). Granularity is behavior, not config: one value per entry per analyte, or per plate when a Plating step ran upstream. Phase I scoping, explicit: uploading ATTACHES, it does not parse — per-instrument import templates (turning entry into verify-against-parsed) are flagged as a future integration; manual entry against the attached export is the Phase I path. Analytical QC entries appear here — this is their instrument home, the CCVs that skipped prep. Criteria whose inputs exist here evaluate the moment a value lands (CCV/ICV recovery vs true value, Tailing Factor, Area Counts, Retention time, Signal-to-noise, Resolution), with per-analyte verdicts — a closing CCV can fail Lead at 87% while Cadmium and Arsenic pass. Failures flag at the bench, travel to QC Review, and do NOT block this step's completion; missing values and a missing required attachment DO block. The screen computes live: everything with complete inputs derives the moment a reading lands — reading × dilution chain ÷ weight, displayed with its inputs for at-a-glance traceability; Matrix Spike recovery appears as soon as spike amount and parent result are both known. Right-click per entry: SEND FOR RE-PREPARATION — a new instance enters the [[Test Pool]] to be batched into a NEW [[Test Batch]] and travels the full workflow again; the original entry's record is retained and marked superseded. SEND FOR RE-ANALYSIS — same prep, new [[Analytical Run]] (Test Batch "may become Analytical Run": the scaffolding's prep-vs-instrument separation, finally used): a new reading field appears on the same entry (the extra-fields pattern applied to readings), prep data carries over, and the prior run's reading is retained; which run is reportable is adjudicated at QC Review. Both actions require a free-form Reason; an e-signature at the moment of the action is recommended and pending confirmation. Both states travel visibly to QC Review. FLAGGED — NEEDS WORK, for the deck's open questions when the Testing section is built: the re-prep/re-analysis mechanism is draft-level — the e-signature-at-action question is unanswered, and the mechanics (how the new pool entry links back, how analytical runs are numbered and managed) need another pass before build.
- **QC Review** — quality control reviews and approves the batch results; this is where QA sign-off lives. TWO-TIER: a top triage screen (QC verdict summary, exceptions docket where every traveled flag requires a disposition + justification — nothing passes silently; send-back dispositions included, inheriting the re-prep/re-analysis needs-work flag) plus TECHNICAL REVIEW through the workflow diagram as a review index — the reviewer opens each step notebook-style and sees the analyst's own execution screen read-only (dilution grid, weighing grid, readings grid — built once, used twice), approving step by step with review marks recorded (who/when). A single flattened full-batch matrix was considered and rejected as the working view — too wide to review, only to scroll — though a flattened export remains available as an audit artifact. Final approval gates on BOTH completeness conditions: every step reviewed AND every exception dispositioned. Segregation is a hard rule enforced by identity: the reviewer must differ from every performer of the reviewed steps. Approval releases the reviewed slice — the whole batch, or a timepoint's data in a study design (the parallel-leaf pattern). One Part 11 signature at batch approval, with per-step review recorded as an explicit clicked "Approve step" action — an affirmative act capturing who and when, not passive scrolling — which is what makes the single-signature model defensible. DECIDED, with a caveat recorded: signature fatigue is real and this is the default, but other labs' GMP preferences may warrant a stricter signature-per-step mode later — a candidate per-lab setting, not an open design question. Wizard config is deliberately near-empty: everything above is a GMP invariant, not a lab preference.

## Also settled here
- **The package pattern** (e.g. ashwagandha dry-basis potency = Withanolides + Loss on Drying): both Requested Tests are created at order time from the package/SKU — a Hold Point in the dependent workflow waits on the named sibling, and the Calculation step combines the two results (withanolides ÷ (1 − LOD) = dry basis). No Split off Test involved; the distinguishing question is whether the second test was knowable at order time.
- **Study designs** (USP 51 PET, agrochemical studies) are long workflows built from existing step types — the workflow builder IS the study designer: inoculation as Preparation, each timepoint as Incubation (with window) → Plating → count Data Entry. The per-timepoint QC Review is a PARALLEL branch off the count step — [[Step Dependency]]'s Parallel type, its first concrete use — terminating as a leaf: the next Incubation depends on the same count step in parallel, so the study clock (calendar-driven; the organisms don't wait for QA) is never blocked by a pending review, while the approved slice becomes available for interim reporting. Completion rule: a [[Test Workflow Instance]] completes only when EVERY branch completes — a pending day-7 review can't block day 14, but the study can't close with it open, so leaf branches can't be silently forgotten. The delivery mechanics belong to the deferred Result Management capability, which will consume these in-workflow approvals rather than inventing its own approval concept. QC Review is therefore repeatable mid-workflow, not only batch-terminal. The top-level workflow diagram — spine plus branches — is the workflow builder's primary visualization.
- [[Electronic Logbook]] integration into workflow steps is deferred to a later session — not designed, not dropped.
- Transfer/Aliquot was proposed as a twelfth type and not adopted.
